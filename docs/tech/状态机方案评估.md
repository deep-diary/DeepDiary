# 状态机方案评估

## 问题分析

当前代码中，三个模式（chat, slideshow, search）的管理逻辑分散在多个地方：
- `switch_to_chat_mode()`, `switch_to_slideshow_mode()`, `switch_to_search_mode()` 分别处理模式切换
- `update_ui()` 根据当前模式更新组件可见性
- `_check_idle_condition_and_apply_switch()` 处理空闲检测和模式切换
- `_handle_service_result()` 处理消息并触发模式切换

这种分散的管理方式导致：
1. **逻辑重复**：组件显示/隐藏逻辑在多个地方重复
2. **状态不一致**：模式切换时可能遗漏某些组件的更新
3. **难以维护**：新增模式或修改逻辑需要在多个地方修改
4. **难以调试**：状态变化不清晰，难以追踪问题

## 状态机方案设计

### 状态定义

class DisplayMode(Enum):
    """显示模式枚举"""
    CHAT = "chat"           # 聊天模式：左侧聊天框，右侧 iframe 轮播人物照片

    SEARCH = "search"        # 自然语言搜索模式：左侧聊天框，右侧 gallery 显示搜索结果

## 优势

1. **逻辑集中**：所有模式切换逻辑集中在一个类中，易于维护
2. **状态清晰**：状态变化有明确的进入和退出逻辑
3. **易于扩展**：新增模式只需添加新的 `enter_X_mode()` 方法
4. **易于测试**：状态机可以独立测试
5. **减少错误**：统一的进入/退出逻辑减少遗漏

## 实施建议

### 阶段 1：重构现有代码
1. 创建 `DisplayModeStateMachine` 类
2. 将现有的 `switch_to_X_mode()` 方法改为调用状态机
3. 将 `update_ui()` 中的模式判断逻辑移到状态机

### 阶段 2：优化
1. 统一组件更新逻辑
2. 统一定时器管理
3. 统一 iframe 管理

### 阶段 3：扩展
1. 添加状态变化日志
2. 添加状态变化回调
3. 添加状态验证

## 结论

**建议采用状态机方案**，理由：
1. 当前代码已经出现了状态管理混乱的问题（如 iframe 未隐藏）
2. 状态机可以让逻辑更清晰，减少错误
3. 未来扩展更容易（如添加新的模式）
4. 代码可维护性更好

**实施优先级**：中等（可以在修复当前问题后逐步重构）
